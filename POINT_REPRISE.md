## 1. Objectif du projet

**OptiLitige** (anciennement « Rclient ») est l'outil web de gestion des litiges SAV et transport du **Groupe Cybertek**. Il remplace le suivi actuel dans une liste SharePoint / Microsoft Lists.

**Cible :** un site en ligne où les agents se connectent avec leur **compte Microsoft Cybertek**. Dans cette version, il est hébergé sur Vercel, avec Supabase pour la base PostgreSQL, le stockage des pièces jointes et la connexion Microsoft (Supabase Auth relié à Entra ID). La version d'origine visait Cloudflare (Workers, D1, R2, Access).

Le projet est né sur ChatGPT Sites. Le code garde la compatibilité avec ce mode (`AUTH_MODE` absent ou `sites`), mais **aucune donnée réelle n'y a été saisie** : il n'y a rien à migrer de là.

## 2. Fonctionnement métier (réponses de l'utilisateur)

**Volumes et équipe**

- **Volumes :** ~1 050 litiges sur SharePoint depuis début 2026, sans compter le SAV. On estime **2 000 à 2 500 par an**.
- **Équipe :** RC ≈ 1,5 personne sur les litiges, SAV 1 à 2, **Service Litige 1 à 2**, Responsables 2 à 3.

**Déroulé d'un litige**

- La **RC**, après un appel client, et le **SAV** (pièces abîmées, fraudes) **créent** les litiges. Le dossier **appartient à son créateur**.
- Le **Service Litige** traite **tous les dossiers en équipe, sans attribution**. Il qualifie le litige (interne ou transporteur), échange avec les commerciaux transporteurs et obtient un résultat.
- **Statuts :** les 5 statuts actuels suffisent (Nouveau, Pris en charge, En attente RC, Résolu, Réouvert). Pas de statut « En attente transporteur ».

**Délais (SLA) :** prise en charge sous **24 h**, réponse transporteur sous **15 jours**. Ils doivent être réglables par les responsables. Ils sont comptés en heures calendaires (week-ends compris).

**Avoirs**

- Ils sont émis dans l'**ERP**, sans API possible pour l'instant.
- La RC les demande au Service Litige, pour raison légale ou satisfaction client.
- Plusieurs avoirs sont possibles sur un dossier, mais c'est rare.

**Transporteurs :** e-mails envoyés depuis la boîte pro de l'agent litige. L'utilisateur veut une **connexion Outlook directe** (envoyer et recevoir depuis l'outil avec l'adresse de l'agent), **pas** un bouton « ouvrir dans Outlook ». Les plateformes transporteurs seront intégrées un jour (forme inconnue).

**Préférences d'organisation**

- Pas de répartition du travail ni d'attribution : ce serait inutile avec 1 à 2 personnes par service.
- Les réglages sont **par équipe, pas par personne**. Exemple : les vues enregistrées sont partagées par service.
- L'utilisateur n'est pas développeur : lui expliquer simplement, en français.

## 3. Contraintes techniques et environnement

**Pile technique (cette version) :** Next.js 16 standard, déployé sur Vercel ; base PostgreSQL Supabase (bibliothèque `pg`, « Transaction pooler »), PGlite en local ; pièces jointes dans Supabase Storage. **Pile d'origine :** vinext 1.0.0-beta.5 (Next.js 16 sur Vite 8) → Cloudflare Worker. Base D1 (SQLite) avec trois tables : `records` (dossier = JSON dans `payload` + `version`), `members`, `settings` (réglages et données diverses par clé). Stockage R2 pour les pièces jointes. React 19, TypeScript strict.

**Poste de travail :** Windows. Le projet est dans `C:\Users\l.lebreton\Desktop\LitigesRC`.

- Node v26.13.0, sans `corepack`. pnpm 11.25.0 a été installé avec `npm install -g`.
- Git 2.56, avec push HTTPS par Git Credential Manager. La connexion GitHub est déjà faite.
- Dans les shells de Claude, ajouter au `PATH` : `/c/Program Files/nodejs` et `$APPDATA/npm`.
- Le connecteur GitHub de l'application Claude est en erreur (« Authorization header is badly formatted ») : on passe par git en ligne de commande.

**Habitudes de travail :**

- Une branche `amelioration/<sujet>` par chantier, des commits en français avec la ligne `Co-Authored-By`.
- On montre le résultat, puis l'utilisateur valide (« envoie sur main »). On fait alors une fusion en avance rapide (fast-forward) sur `main`, un push, et on supprime la branche.

**Fin de lignes :** `core.autocrlf=true` ; Prettier est en `endOfLine: auto`.

**Mode démonstration :** données fictives stockées dans le `localStorage` du navigateur (`rclient-demo-v2`). L'**espace réel local** utilise la base D1 locale de `pnpm dev`, avec une connexion simulée « Seedy » (`/signin-with-chatgpt`).

**Noms techniques volontairement inchangés :** clés `rclient-demo-*`, worker `rclient`, base `rclient-db`.

## 8. Problèmes restants et points d'attention

- **Mise en ligne bloquée** : il faut les comptes Supabase et Vercel au nom de Cybertek, un nom de domaine (ex. `litiges.cybertek.fr`) et une application Entra créée par l'administrateur Entra. Voir DEPLOIEMENT-SUPABASE-VERCEL.md et A-FINALISER-AVEC-IT.md.
- **Le premier compte connecté devient propriétaire et Responsable** : ce doit être le chef de projet, juste après la mise en ligne.
- **Validation des avoirs** : la règle par défaut (geste commercial > 150 € → responsable) reste à confirmer par l'utilisateur.
- **RGPD** : les durées sont à faire valider par le DPO ; la purge automatique n'est pas codée.
- Les **pièces jointes** ne sont pas comprises dans les sauvegardes de la base Supabase : il faut planifier une copie du compartiment `pieces-jointes`.
- Les **dossiers importés avec l'ancien SheetJS** peuvent avoir des dates décalées d'un jour. Aucun import réel n'a encore eu lieu.
- Dans le **guide**, la capture de la webcam montre l'image de test d'une caméra simulée : à remplacer par une vraie photo.
- **Délais calendaires** : un passage aux jours ouvrés est possible si l'utilisateur le demande.
- La base de test locale (`.donnees-locales`) contient des dossiers et des comptes de test créés par les tests API. Ce n'est pas grave, c'est local.
